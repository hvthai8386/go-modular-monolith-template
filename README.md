# go-modular-monolith-template

A template for a Go service built as a **modular monolith**: one binary, one database, one gRPC
server with a REST gateway in front of it, and inside it independent modules that each follow the
**hexagonal** (ports and adapters) shape. The dependency rule is enforced by the linter, not by
convention.

Borrowed from [go-clean-template](https://github.com/evrone/go-clean-template), with three changes:

| go-clean-template | this template |
|---|---|
| One service, layers at the top level | Many modules, each with its own `core` and `adapter` |
| Interfaces live next to the use case that needs them | Ports are explicit packages: `port/in` (driving) and `port/out` (driven) |
| Rule "inner layer imports only stdlib" is documented | Rule is checked in CI by `depguard` |

## Architecture at a glance

```
 REST client ──▶ HTTP server ──▶ grpc-gateway ──loopback──┐
                                                         ▼
 gRPC client ─────────────────────────────────────▶ gRPC server ──▶ interceptors
                                                                        │
            internal/monolith (hosts everything above, owns the DB pool)│
 ═══════════════════════════════════════════════════════════════════════╪═══════
            internal/<module>                                           ▼
                                                            adapter/in/grpc   (driving adapter)
                                                                  │ calls
                                                                  ▼
                       ┌──────────────── core (stdlib only) ──────────────────┐
                       │   port/in  ◀── implemented by ──  usecase            │
                       │                                      │ uses         │
                       │                                      ▼              │
                       │                                   domain            │
                       │                                      │              │
                       │   port/out ◀────── depends on ───────┘              │
                       └──────────────────────────────────────────────────────┘
                                                                  ▲ implements
                                                                  │
                                                            adapter/out/postgres (driven adapter)
                                                                  │
                                                                  ▼
                                                              PostgreSQL
```

- **core** is pure Go: domain types with behaviour, the ports it offers (`port/in`) and the ports it
  needs (`port/out`), and use cases that implement the former by calling the latter. `depguard`
  rejects any import there that is not the standard library or the module's own core.
- **adapters** translate between the outside world and the ports. gRPC handlers map protobuf to
  domain calls; the Postgres adapter implements `port/out` on top of the [sqlc](https://sqlc.dev)
  generated package in `internal/db`.
- **monolith** wires modules together. A module exposes `Name()` and `Register(ctx, Deps)`, and
  `Deps` is everything it may register against: the gRPC server, the gateway mux, the loopback
  connection, the database pool and a logger tagged with the module name.
- **REST is generated, not written.** HTTP routes are `google.api.http` annotations in the proto
  file; grpc-gateway serves them by dialling the gRPC server over loopback, so REST and gRPC traffic
  pass the same interceptors.

The full set of rules is in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md); the reasoning behind
each choice is in [docs/adr](docs/adr).

## Repository layout

```
cmd/app/                     entry point: config, logger, monolith.New, Run
api/                         buf config and .proto files (source of truth for the API)
gen/                         protobuf, gRPC and gateway code generated by buf (committed)
db/
  migrations/                goose SQL migrations, one history for the one database
  schema/                    tables created by tools (goose's version table), for sqlc only
  query/<module>.sql         sqlc queries, one file per module
internal/
  db/                        Go code generated by sqlc from db/ (committed)
  config/                    env-based configuration
  logging/                   slog setup
  monolith/                  module registry, servers, interceptors, graceful shutdown
  versioning/                sample module
    module.go                wiring of this module, from the outside in
    core/domain/             entities and value objects
    core/port/in/            driving ports (+ inmock/ function-field mocks)
    core/port/out/           driven ports (+ outmock/ function-field mocks)
    core/usecase/            application services implementing port/in
    adapter/in/grpc/         gRPC handlers and gateway registration
    adapter/out/postgres/    port/out implementation on top of internal/db
docs/                        ARCHITECTURE.md and ADRs
.github/workflows/           ci.yml (lint, generate-and-diff, test) and migrate.yml
```

## Quick start

Prerequisites: Go 1.26+, [buf](https://buf.build/docs/installation),
[golangci-lint](https://golangci-lint.run) v2, and a PostgreSQL database. sqlc and goose are run
through `go run` at pinned versions, nothing else to install.

```sh
export DATABASE_URL='postgresql://user:password@localhost:5432/app?sslmode=disable'

make migrate        # apply migrations with the goose CLI
make run            # gRPC on :9090, HTTP on :8080

curl -s localhost:8080/v1/versioning/version
# {"appVersion":"0.0.0-dev","goVersion":"go1.26.3","databaseVersion":"PostgreSQL 18.1 ...","schemaVersion":"1"}
```

Configuration is read from the environment; see
[internal/config/.env.example](internal/config/.env.example).

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | required | PostgreSQL connection string |
| `APP_VERSION` | `0.0.0-dev` | Semantic version reported by the versioning module |
| `GRPC_ADDR` | `:9090` | gRPC listen address |
| `HTTP_ADDR` | `:8080` | HTTP (gateway, health) listen address |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` or `error` |
| `ENV` | `development` | `production` switches logs to JSON |

### Endpoints

| REST | gRPC | Purpose |
|---|---|---|
| `GET /v1/versioning/version` | `versioning.v1.VersioningService/GetVersion` | App, Go, PostgreSQL and schema versions |
| `GET /healthz` | `grpc.health.v1.Health/Check` | Process is up |
| `GET /readyz` | | Database reachable |

gRPC reflection is enabled, so `grpcurl -plaintext localhost:9090 list` works.

### Make targets

| Target | What it does |
|---|---|
| `make generate` | `buf lint`, `buf generate`, `sqlc generate`. CI fails if the output is not committed. |
| `make lint` | `golangci-lint run`, including the `depguard` core rule |
| `make test` | `go test -race ./...`; Postgres tests run only when `DATABASE_URL` is set |
| `make migrate` | `goose up` |
| `make migrate-status` | `goose status` |
| `make migrate-create NAME=add_orders` | Create a new timestamped SQL migration |
| `make run` | Start the app |

## Adding a module

1. Create `internal/<name>/` with `core/domain`, `core/port/in`, `core/port/out`, `core/usecase`,
   and the adapters you need. Copy `internal/versioning` as a starting point.
2. Add the module's core to the `depguard` allow list in `.golangci.yml`.
3. Put the API in `api/<name>/v1/<name>.proto` with `google.api.http` annotations, and the SQL in
   `db/query/<name>.sql`, then `make generate`.
4. Write `module.go`: parse configuration, build driven adapters, build use cases, build driving
   adapters, register them on `deps.GRPCServer` and `deps.GatewayMux`.
5. Add `&<name>.Module{...}` to the `monolith.New` call in `cmd/app/main.go`.

## Adding a migration

```sh
make migrate-create NAME=add_orders_table   # creates db/migrations/<timestamp>_add_orders_table.sql
make migrate                                # applies it locally
```

The `migrate` workflow applies pending migrations when a commit on `main` touches `db/migrations/`,
using the `DATABASE_URL` secret of the `production` environment. Migrations therefore reach the
database **before** the matching app version is deployed, so every migration must be
backward-compatible with the version currently running: add columns and tables freely, drop or
rename them only one release after the code stopped using them.

## Testing

- **Core and handlers** use hand-written function-field mocks in `port/in/inmock` and
  `port/out/outmock`. A test assigns the function it needs; an unassigned function panics with its
  name, so a forgotten stub fails loudly instead of returning zero values.
- **Driven adapters** run against a real database and skip when `DATABASE_URL` is unset. CI
  provides a PostgreSQL service container and runs `make migrate` first.
